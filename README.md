# ProseLab

A writing practice app built with Next.js App Router, React, and TypeScript.
Writers study curated passages, practise craft constraints, receive AI feedback,
listen to their work, and share submissions with the community.

## Local development

Use Node.js 24 LTS and npm. Install the locked dependencies with `npm ci`, copy
`.env.example` to `.env.local`, and fill in the credentials for your development
services. Start the app with `npm run dev` and open http://localhost:3000.

Supabase needs both browser publishable credentials and server credentials. The
service role key, AI keys, and billing secrets must never use a `NEXT_PUBLIC_`
prefix. Use a development Supabase project and billing sandbox for local writes.
The checked-in migrations are incremental changes to an existing database, not
a complete initial schema; a fresh Supabase project also needs the base tables,
RLS policies, and RPC functions referenced in `types/database.types.ts`.

## How it fits together

| Location | Responsibility |
| --- | --- |
| `app/` | Pages, server actions, and API routes |
| `components/` | Exercise flow, editing, feedback, community, and account UI |
| `data/passages/` | Curated passages grouped by craft category |
| `hooks/useExtractAnalysis.ts` | Cancelable analysis requests and bounded exercise cache |
| `hooks/useSpeech.ts` | ElevenLabs playback and audio resource cleanup |
| `lib/supabase/` | Browser, server, and middleware session clients |
| `lib/plan.ts`, `lib/trial.ts` | Plan entitlements, usage, and trial rules |
| `lib/explore-feed.ts` | Public submission feed for server-rendered pages |
| `supabase/migrations/` | Incremental database changes |

`middleware.ts` refreshes the session and authenticates protected requests with
one Supabase lookup. Public billing webhooks authenticate through their own
signature checks. Server actions and API handlers also check authentication
where required; the service role client bypasses RLS and must remain server-only.

Passage analysis is generated by Anthropic and cached in `passage_analyses`.
Writing feedback, example generation, assessment, and playground each have API
routes. Audio comes from ElevenLabs, including dialogue voices; it does not use
the browser's built-in speech synthesis. Whop handles current purchases, with
Stripe retained for legacy subscriptions.

## Verification

```bash
npm test
npm run typecheck
npm run lint
npm run build
```

Tests use Node's test runner with `tsx`; hook lifecycle tests use React Testing
Library and jsdom. Network requests and audio are mocked, so the tests do not
call AI services, charge billing accounts, or require `.env.local`. Production
builds need the server environment configured and access to Google Fonts for
the `next/font` download.

## Billing and purchase email flow

- Supabase Auth creates the stable application user ID.
- Whop is the active checkout provider. Its webhook and verified checkout
  receipt both upsert the provider-neutral `subscriptions` row.
- Successful `active` or `trialing` subscriptions update the matching Loops
  contact to `userGroup: Core User`, which starts the live purchase sequence.
  The same webhook path also sets Resend contact `plan_tier` from the app
  `plan_id` (`core`, `premium`, `pre_release_yearly`, …) and adds the contact
  to the Paying Users segment (all payers).
- A scheduled cancellation remains paid until Whop deactivates the membership.
  Only terminal states such as `canceled` or `expired` return the contact to
  `userGroup: Free User` and Resend `plan_tier: free` (removed from Paying
  Users).
- Stripe remains supported for legacy subscriptions and uses the same Loops
  and Resend contact sync. Webhook failures return an error so Stripe or Whop
  can retry.

Production requires `LOOPS_API_KEY` and `RESEND_API_KEY` in addition to the
Supabase and billing provider secrets listed in `.env.example`. Optional
`RESEND_PAYING_SEGMENT_ID` overrides the default Paying Users segment.

Before rollout, preview the existing-purchaser backfill without changing Loops:

```bash
npm run sync:loops-purchasers
```

After reviewing the dry run and deploying the same configuration, apply it once
with `npm run sync:loops-purchasers -- --apply`. The command is idempotent, only
targets active or trialing subscriptions, and is safe to rerun after a partial
failure.
